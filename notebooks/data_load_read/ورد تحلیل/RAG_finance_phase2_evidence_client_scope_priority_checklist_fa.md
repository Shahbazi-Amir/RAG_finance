# چک‌لیست اولویت‌دار — ممیزی فاز دوم، گزارش کارفرما و تعیین مرز فاز سوم/چهارم

**پروژه:** RAG_finance  
**تاریخ تنظیم:** ۳۱ اکتبر ۲۰۲۶  
**وضعیت:** نسخهٔ اولیهٔ برنامهٔ بررسی؛ نه گزارش پذیرش نهایی  
**دامنهٔ عملیات:** بررسی و تولید سند محلی؛ هیچ عملیات Git، API یا Deploy مجاز نیست.

## اصل تصمیم‌گیری

چهار وضعیت با هم یکی نشوند: `کار پیاده‌سازی‌شده`، `تست فنی PASS`، `Gate کیفیت PASS` و `Release/تحویل رسمی ACCEPTED`. هر ادعا باید به نسخهٔ Notebook، مسیر Artifact، SHA، محدودهٔ آزمون و تصمیم Gate وصل شود. فایل Word قدیمی صرفاً سند تاریخی است و باید با اجرای بعدی تطبیق داده شود.

## وضعیت‌هایی که فعلاً می‌توان ثبت کرد

- [x] نقشهٔ ماژولار فاز سوم: ۲۶ ماژول M00–M25 وجود دارد.
- [x] نقشهٔ عملیاتی فاز چهارم: ۱۳ بستهٔ P4-01 تا P4-13 وجود دارد؛ **کفایت آن برای درخواست واقعی کارفرما هنوز تأیید نشده است**.
- [x] NB23 روی ورودی NB22A: فایل Run All ارسالی شامل ۱۲ سل Python با execution_count متوالی ۱ تا ۱۲ و صفر Error Output بود؛ C012 تعداد ۵۴/۵۴ آزمون مستقل و ۲۸ فایل ورودی را گزارش کرد. `formal_readiness=BLOCKED` باقی ماند.
- [x] نتیجهٔ مقایسهٔ گزارش‌شدهٔ Retrieval روی همان ۱۲ سؤال پایلوت: `onnx400_fusion` نسبت به NB22D پیشرفت کرده، ولی Recall@10=79.17% در برابر حد 85% و nDCG@10=63.06% در برابر حد 75%، هنوز Gate را عبور نمی‌کند. Hit@10=100% بدون حد پذیرش تعریف‌شده است. این گزارش پایلوت، Release رسمی نیست.
- [ ] Word کارفرما (احتمالاً تا NB13) دریافت و با فایل‌های واقعی تطبیق داده شود؛ هنوز در مواد این گفتگو موجود نیست.
- [ ] پوشش کامل فاز دوم طبق نقشه، برای همهٔ NB00–NB23 و Gateها مستقل بررسی شود.

## P0 — پیش‌نیازهای تصمیم کارفرما و جلوگیری از دوباره‌کاری

### P0-01 — جمع‌آوری نسخه‌های مرجع
- [ ] دریافت Word گزارش قبلی و تعیین تاریخ، Snapshot و آخرین Notebook پوشش‌داده‌شده در آن.
- [ ] ثبت نسخهٔ دقیق نقشه‌های فاز ۲، ۳، ۴، و نقشهٔ کلان؛ از آمیختن نسخه‌های قدیمی و جدید خودداری شود.
- [ ] تهیهٔ فهرست NB00–NB23 و NBهای انشعابی؛ برای هرکدام آخرین فایل/نسخه، خروجی، گزارش، Gate، SHA و محدودیت ثبت شود.
**خروجی:** `evidence_inventory` و فهرست «آنچه Word گفته / آنچه اکنون ثابت است».  
**پایان:** هیچ ادعای عمدهٔ پیشرفت بدون منبع و نسخه باقی نماند.

### P0-02 — ممیزی تکمیل واقعی فاز دوم
- [ ] پوشش هر الزام نقشهٔ فاز دوم با Notebook/Artifact/Report متناظر بررسی شود.
- [ ] چهار ستون جدا ثبت شود: پیاده‌سازی، اجرای تمیز، کیفیت/Benchmark و پذیرش Release.
- [ ] موارد NB14–NB23، NB21 شاخه‌ای و NB22A/B/C/D با مرجع واقعی تفکیک شوند؛ وجود یا پذیرش نسخه از روی نام فرض نشود.
- [ ] Metrics به همراه مجموعهٔ آزمون، تعداد سؤال، baseline، threshold و نسخه ثبت شود؛ پایلوت ۱۲سؤالی با Golden اصلی ادغام نشود.
- [ ] برای هر نقص، «کار لازم»، «کار موکول‌شده»، «کار خارج از دامنه» و «نیازمند تصمیم کارفرما» جدا شود.
**خروجی:** ماتریس `Roadmap Requirement → Evidence → Test → Gate → Gap` با وضعیت قابل‌ممیزی.  
**پایان:** روشن باشد فاز دوم کجا واقعاً Done است، کجا Draft PASS است و کجا Blocked.

### P0-03 — تعیین نیاز واقعی کارفرما و تحویل آذر
- [ ] صورت‌جلسهٔ Scope/تعهد زمانی: آیا تحویل، پایلوت محدود است یا Production عمومی؟
- [ ] انتظار دربارهٔ پنل: عملیات محدود فاز سوم یا مدیریت گستردهٔ محتوا/آزمون/قواعد/کاربران؟
- [ ] قابلیت‌های محصول: ثبت‌نام، تاریخچه، پاسخ مستند، حافظهٔ مکالمه، امنیت، ظرفیت، بازخورد، حذف داده، دسترس‌پذیری و موبایل با معیار پذیرش مشخص شوند.
- [ ] تفاوت «قابل نمایش»، «قابل استفادهٔ محدود» و «آمادهٔ Production» برای کارفرما روشن و تصویب شود.
**خروجی:** صورت‌جلسهٔ تصمیمات و جدول `ضروری برای آذر / فاز چهارم / موکول به پس از پایلوت`.  
**پایان:** هیچ قابلیت مبهمی به ایجنت‌ها سپرده نشود.

## P1 — گزارش مصور و معماریِ بدون دوباره‌کاری

### P1-01 — ساخت گزارش کارفرما (دو سطح)
- [ ] Word قدیمی تا آخرین نقطهٔ معتبر حفظ، اصلاح و ادامه داده شود؛ خروجی NB14–NB23 اضافه شود.
- [ ] گزارش مدیریتی قابل‌فهم و ضمیمهٔ فنیِ قابل دفاع از هم جدا شوند.
- [ ] هفت تصویر/نمودار با شواهد واقعی تولید شود: ۱) نمای کل چهار فاز؛ ۲) جریان سه منبع تا Dataset؛ ۳) Chunk/Embedding/Index/Retrieval؛ ۴) Answer/Claim/Citation/Safety؛ ۵) Notebookها و وضعیت Gate؛ ۶) نمودار قبل/بعدِ هم‌مقیاسِ Metricها؛ ۷) مرز فاز سوم/چهارم و وابستگی‌ها.
- [ ] روی هر شکل مشخص شود `انجام‌شده`، `در حال بهبود`، `طرح آینده` یا `Blocked`؛ تصاویر UI طراحی‌شده با UI موجود اشتباه نشوند.
**خروجی:** گزارش Word به‌روز + نسخهٔ ارائه‌ای مصور + پیوست شواهد.  
**پایان:** کارفرما بتواند وضع موجود، مانع‌ها، تصمیم‌های خود و قدم بعد را بدون خواندن Notebook بفهمد.

### P1-02 — تفکیک قطعی فاز سوم و چهارم
- [ ] همهٔ قابلیت‌ها از نقشهٔ کلان، نقشهٔ اجرایی ۲۶ماژولی فاز ۳ و ۱۳بسته‌ای فاز ۴ به یک Capability Matrix منتقل شوند.
- [ ] مشترک‌ها فقط یک‌بار طراحی شوند: Identity/Consent، PostgreSQL، RBAC/RLS، Audit، API versioning، Web design system، Admin shell و Event model.
- [ ] تعیین شود کدام قابلیت در فاز سوم واقعاً فعال است و کدام صرفاً Extension Point فاز چهارم دارد؛ از ساخت جدول/پنل فرضی زودهنگام پرهیز شود.
- [ ] وابستگی‌های فاز چهارم به Release فاز دوم و زیرساخت فاز سوم مشخص شود.
**خروجی:** `Phase3–Phase4 Capability & Ownership Matrix` و نمودار معماری مشترک.  
**پایان:** هیچ بخش حیاتی دوبار ساخته نشود و هر قابلیت دقیقاً یک مالک و مرحلهٔ پذیرش داشته باشد.

### P1-03 — ممیزی نقشهٔ فاز چهارم قبل از قرارداد
- [ ] هر P4-01 تا P4-13 از نظر ورودی، خروجی، وابستگی، owner، هزینه، داده، آزمون و Gate بررسی شود.
- [ ] اعتبارسنجی علمی Assessment، قواعد مالی و Calculators با متخصص حوزه برنامه‌ریزی شود؛ کدنویسی جای تصویب علمی/حقوقی را نگیرد.
- [ ] طراحی پنل مدیریت: Role matrix، Workflow تأیید، Audit، مدیریت Release، Rights و دسترسی به PII دقیق شود.
- [ ] سنجش Outcome، پایلوت، Consent، حذف داده و Human Referral با نیاز کارفرما تطبیق داده شود.
- [ ] مدت ۲ تا ۳ ماه فقط بعد از تعیین Scope و منابع اجرایی، به Baseline قابل پیگیری تبدیل شود.
**خروجی:** Gap analysis فاز چهارم + سؤال‌های قابل تصمیم در جلسهٔ کارفرما.  
**پایان:** معلوم باشد نقشهٔ فعلی کافی است، نیاز به اصلاح دارد یا بعضی بخش‌ها خارج از قراردادند.

## P2 — شروع امن اجرای موازی

### P2-01 — چارچوب مأموریت ایجنت‌ها
- [ ] تا قبل از تأیید Scope و Contractها به هیچ ایجنت دستور «کل محصول را بساز» داده نشود.
- [ ] مخزن اصلی فقط خواندنی؛ محیط توسعهٔ ایجنت‌ها جدا، خصوصی و مبتنی بر Snapshot/Commit مشخص باشد؛ Secret، دادهٔ خصوصی و فایل حجیم غیرضروری منتقل نشود.
- [ ] قرارداد مشترک API، DB، Auth، Citation، Admin و Error model پیش از کار موازی تثبیت شود.
- [ ] برای هر ایجنت Scope، فایل‌های مجاز، تست مثبت/منفی، حد هزینه، معیار توقف، گزارش diff و Gate تعریف شود.
- [ ] یکپارچه‌سازی فقط پس از تست‌های واقعی؛ بدون Push/Commit/Deploy خودکار به مخزن اصلی و بدون تأیید صریح.
**خروجی:** دستور کار قابل سپردن به هماهنگ‌کننده و چهار بستهٔ مستقل ایجنتی.  
**پایان:** نتیجهٔ کار با آزمون پذیرش قابل کنترل باشد، نه بررسی دستی تک‌تک خطوط.

## خروجی‌های جلسه با کارفرما

- [ ] گزارش پیشرفت شواهدی فاز دوم با نمودارها.
- [ ] نمایش شفاف `What is done / What remains / What blocks release`.
- [ ] ماتریس قابلیت‌ها و محدودهٔ فاز ۳ و فاز ۴؛ پنل مدیریت به‌صورت جداگانه تصمیم‌گیری شود.
- [ ] دو زمان‌بندی مشروط: نسخهٔ قابل‌ارائهٔ آذر و محصول نهاییِ دارای Gateهای Production.
- [ ] بودجه و مسئولیت‌های Hosting، مدل، دادهٔ شخصی، امنیت و پذیرش کارفرما مشخص شوند.
- [ ] تصمیم‌های جلسه با نسخه و مسئول تصمیم ثبت شوند.
