# دستورالعمل اجرای اقدام‌محور، تجمیعی و جلوگیری از دوباره‌کاری

**پروژه:** RAG_finance — فاز دوم  
**نسخه:** ۱٫۰ — ۲۸ اکتبر ۲۰۲۶  
**مبنای تدوین:** دستور مستقیم کاربر در همین گفتگو و قواعد همکاری خوانده‌شدهٔ همین پروژه.  
**محل قرارگیری پیشنهادی:** پوشهٔ `notebooks/data_load_read/ ورژن جدید ارسال/`

این سند مکمل دستورالعمل‌های موجود است و روش اجرای اقدامات چک‌لیست را روشن می‌کند. قراردادهای فریز‌شده، آستانه‌ها، سیاست هزینه، دامنهٔ پذیرش و تصمیم‌های معتبر قبلی را تغییر نمی‌دهد. وضعیت جاری هر اقدام از آخرین خروجی و شاهد معتبر همان اقدام خوانده شود؛ این سند دفتر وضعیت اجرا نیست.

## ۱. مسئله و اصل همکاری

طبق توضیح کاربر، NB20 و NB21 هرکدام در سه بخش A، B و C انجام شده‌اند. حجم هر بخش در حدود ۳۰۰ سل کد و با Markdownها حدود ۶۰۰ سل بوده است؛ این اعداد شرح تقریبی کاربرند، نه شمارش تازهٔ فایل‌ها. کار وسیعی انجام شده و بخشی از دشواری ادامه، پیدا‌کردن و مصرف درست همان کارهاست.

کاربر مشکل این مسیر را الزاماً API اضافی ندانسته است؛ خواندن مکرر مخزن، رعایت‌نشدن روش همکاری، تشخیص اشتباه «انجام نشده» و تولید سل‌های پراکنده نیز دوباره‌کاری ایجاد کرده‌اند.

**اصل اجرایی: قبل از ساختن یا اجرای دوباره، کار موجود را پیدا کن، دامنه و نسخه‌اش را بفهم و در صورت کفایت مصرف کن. سپس فقط شکاف واقعی را انجام بده.**

مطالعهٔ کافی برای رفع ابهام لازم است؛ اما مطالعهٔ انجام‌شده باید با ارجاع قابل استفاده باقی بماند تا در هر نوبت کل مخزن دوباره خوانده نشود. سرعت با حذف بررسی لازم یا تضعیف معیار پذیرش به دست نمی‌آید.

## ۲. واحد کار: شمارهٔ اقدام در چک‌لیست

پیش از هر بستهٔ اجرایی، دستیار باید روشن کند:

1. نوت‌بوک مسئول کدام است و شماره و عنوان دقیق اقدام چیست؟
2. این اقدام چه نتیجه‌ای باید بدهد و شرط پایانش چیست؟
3. خود این اقدام چند زیرکار مشخص دارد؟ زیرکارها با شماره و عنوان کوتاه فهرست شوند.
4. کدام زیرکار قبلاً انجام شده، کدام فقط اتصال یا تطبیق لازم دارد و کدام واقعاً باقی است؟
5. همهٔ زیرکارهای باقی‌مانده در یک سل کامل قابل انجام‌اند یا به چند بستهٔ وابسته نیاز دارند؟

شمارهٔ اقدام، شمارهٔ زیرکار، شمارهٔ بسته و شمارهٔ سل چهار شناسهٔ جدا هستند. یک اقدام ممکن است چند زیرکار داشته باشد و چند زیرکار مرتبط ممکن است در یک سل انجام شوند. افزایش تعداد سل هدف نیست. شماره‌های تاریخی چک‌لیست و نوت‌بوک برای مرتب‌سازی ظاهری بازنویسی نشوند.

در صورت چندبسته‌ای‌بودن، از ابتدا بگو: «اقدام … شامل … زیرکار است؛ در … بسته انجام می‌شود؛ اکنون بستهٔ … را پیش می‌بریم.» تعداد زیرکارها از الزام واقعی همان اقدام تعیین شود، نه از یک عدد ثابت برای همهٔ اقدامات.

## ۳. بررسی آفلاین و مصرف شواهد پیش از کد اجرایی

ابتدا نقشهٔ مربوط، متن کامل اقدام و شرط پایانش، یادداشت دامنهٔ تیک‌ها، آخرین گزارش نهایی و Handoff همان بخش خوانده شوند. سپس شواهد لازم دنبال شوند:

| منبع | هدف بررسی |
| --- | --- |
| چک‌لیست و تصمیم جدید | شناخت دقیق الزام و دامنهٔ بسته‌شده یا باز |
| گزارش نهایی، Manifest، Release و Handoff | یافتن نسخه و مسیر معتبر بدون بازسازی Producer |
| خروجی ذخیره‌شده و Cache/Checkpoint | مصرف نتیجهٔ قبلی و تشخیص کار واقعاً ناقص |
| سل تولیدکننده و کد معتبر موجود | فهم منطق، Schema، روش اتصال و کنترل‌ها در صورت نیاز |
| داده یا رکورد مربوط | رفع شکاف مشخصی که از منابع بالاتر حل نشده است |

بررسی آفلاین یعنی پیش از ارسال مدل، وجود فایل، نسخه، Schema، تعریف هش، شناسه، اتصال، پوشش، نتیجهٔ قبلی و Attemptها به‌قدر نیاز بررسی شوند. این عبارت به معنی الزام دریافت دوبارهٔ بایت تمام مخزن برای هر اقدام نیست. خواندن مخزن برای بررسی اسناد، با فراخوانی API مدل تفاوت دارد.

اگر منبع لازم هنوز خوانده نشده، صریح گفته شود؛ دریافت فایل، خواندن خلاصه، خواندن کامل و اعتبارسنجی بایت Artifact یکسان نیستند. «همه را خواندم» فقط با دامنهٔ واقعاً کامل گفته شود.

### وضعیت زیرکارها پس از بررسی

| وضعیت توصیفی | رفتار لازم |
| --- | --- |
| انجام‌شده و قابل مصرف | استفاده از نتیجه و ثبت ارجاع؛ اجرا یا داوری تکرار نشود |
| انجام‌شده ولی نیازمند اتصال/Adapter | اتصال مکانیکی مستند؛ نتیجهٔ معنایی ساخته یا عوض نشود |
| شواهد موجود ولی نیازمند تطبیق | فقط همان اختلاف نسخه، دامنه، هش یا قرارداد بررسی شود |
| دسترسی فعلی ناکافی | فایل یا خروجی دقیق لازم مشخص شود؛ نبود کار نتیجه نشود |
| تلاش قبلی با نتیجهٔ نامعلوم | ابتدا تطبیق Attempt و پاسخ؛ ارسال مجدد خودکار نشود |
| شکاف واقعی پس از بررسی کافی | فقط همان زیرکار وارد برنامهٔ اجرای تازه شود |
| FAIL/BLOCKED ثبت‌شده | وضعیت با شاهد و مسئول حفظ شود؛ گزارش‌سازی آن را PASS نمی‌کند |

نام‌های این جدول، توضیح روش‌اند؛ مجوز تغییر Enum یا Schema موجود نیستند.

## ۴. جلوگیری از خواندن مکرر و نتیجه‌گیری «انجام نشده»

برای هر اقدام، یک ثبت کوتاه و قابل ادامه نگه داشته شود؛ از دفتر شواهد معتبر موجود استفاده شود و دفتر موازی غیرضروری ساخته نشود:

`شمارهٔ اقدام/زیرکار → Producer و سل → مسیر/نسخه/نوع هش → دامنه → تصمیم قبلی → قابلیت مصرف → شکاف باقی‌مانده → بستهٔ بعد`

پس از ثبت این اتصال، در ادامهٔ همان نسخه به آن رجوع شود. بازخوانی تازه فقط برای تغییر مؤثر ورودی یا نسخه، تعارض، خطای مشخص، محدودیت شاهد قبلی یا نیاز واقعی مصرف‌کننده انجام شود. تغییر HEAD به‌تنهایی دلیل بازخوانی تمام فایل‌های نامرتبط نیست؛ اثر تغییر روی وابستگی مربوط بررسی شود.

موارد زیر به‌تنهایی اثبات «انجام نشده» نیستند:

- نبود Artifact در GitHub، خصوصاً فایل‌های ignored یا محلی؛
- محدودیت connector در خواندن نوت‌بوک حجیم؛
- تفاوت نام فایل، فیلد، سل یا محل قرارگیری؛
- نبود شناسهٔ مستقیم در یک Export یا نیاز به Adapter؛
- ناقص یا قدیمی‌بودن index، خلاصه یا گزارش مقدماتی؛
- شکست یک Parser یا Join؛
- وجود متن تاریخی OPEN در کنار خروجی نهایی جدیدتر.

اگر شاهد کافی پیدا نشد، بگو: «در منابع بررسی‌شده احراز نشد» و دامنهٔ جست‌وجو و شکاف را مشخص کن. دربارهٔ آنچه معلوم نیست بگو «مطمئن نیستم». برای احتیاط، کل جمعیت دوباره اجرا نشود.

## ۵. اجرای تجمیعی در کمترین بستهٔ لازم

پیش‌فرض، **یک سل کامل و تجمیعی برای تمام زیرکارهای مرتبط و آمادهٔ همان بسته** است. سل باید نتیجهٔ قابل بررسی اقدام را جلو ببرد؛ مجموعه‌ای از سل‌های صرفاً کشف، شمارش و تشخیص جای خروجی اصلی را نگیرد.

تجمیع می‌تواند شامل بارگذاری ورودی‌های مشخص، کنترل قرارداد، مصرف نتیجهٔ قبلی، انجام شکاف، اعتبارسنجی و ثبت خروجی باشد؛ فقط مراحلی که برای همان اقدام لازم‌اند. پیش‌بررسی‌های معتبر قبلی بدون علت تکرار نشوند.

چند بسته فقط با دلیل اجرایی روشن مجاز است، مانند:

- وابستگی واقعی به خروجی بستهٔ قبل؛
- نیاز به بررسی خروجی کاربر برای تصمیم بعدی؛
- شرط توقف پیش از API یا تصمیم واقعی دربارهٔ دامنه/هزینه؛
- عملیات طولانی با Checkpoint و Resume مستقل؛
- اندازه یا پیچیدگی‌ای که اصلاح و بررسی یک سل را دشوار می‌کند.

در این حالت ابتدا تعداد بسته‌ها، زیرکارهای هرکدام، وابستگی و خروجی پایانشان مشخص شود. سل غول‌آسا به قیمت حذف کنترل، قابلیت توقف یا امکان اصلاح ساخته نشود. شکست یک وابستگی، مرحلهٔ وابسته را متوقف کند؛ کار مستقل بی‌دلیل متوقف نشود.

## ۶. قالب ثابت پاسخ و Markdown همراه سل

کاربر کد را در VS Code/Jupyter اجرا می‌کند و خروجی واقعی می‌فرستد. دستیار پس از بررسی خروجی، توضیح کوتاه و گام کامل بعدی را می‌دهد. فایل Python یا وصلهٔ پراکنده جای سل کامل چت را نگیرد.

پاسخ اجرایی سه بخش دارد:

1. توضیح کوتاه فارسی: اقدام فعال، تعداد زیرکارها، انجام‌شده‌ها، کار همین بسته و نتیجهٔ مورد انتظار.
2. یک باکس مستقل `markdown` با متن فارسی RTL برای سل توضیحی نوت‌بوک.
3. یک باکس مستقل `python` با سل کامل شماره‌دار، عنوان یکتا و تمام منطق لازم همان بسته.

الگوی زیر فقط قالب مستندسازی است؛ جای کد اجرایی واقعی را نمی‌گیرد. در پاسخ واقعی، جای‌نگهدارها با اطلاعات بررسی‌شده پر شوند.

```markdown
<div dir="rtl" align="right">

### [شناسهٔ سل] — اقدام [شماره]: [عنوان اقدام]

- هدف و شرط پایان اقدام: …
- این اقدام شامل … زیرکار است: …
- زیرکارهای انجام‌شده و شواهد قابل مصرف: …
- زیرکارهای باقی‌مانده: …
- بستهٔ فعلی: … از …؛ زیرکارهای این سل: …
- ورودی و نسخهٔ واقعی: …
- خروجی و کنترل پذیرش این بسته: …
- API تازه، هزینه و شرط توقف: …

</div>
```

خط اول سل کد، شناسهٔ معتبر همان نوت‌بوک و عنوان روشن داشته باشد. سل به توابع تعریف‌نشده، متغیر نوت‌بوک قبلی یا History کرنل متکی نباشد. وابستگی روشن به Imports و سل‌های قبلی همین نوت‌بوک مجاز است. قاعدهٔ شروع نوت‌بوک تازه، شامل Imports/Bootstrap جدا، همچنان حفظ می‌شود؛ برای ادامهٔ فایل موجود Bootstrap از صفر تکرار نشود.

## ۷. API فقط برای شکاف اثبات‌شده

پس از بررسی آفلاین و مصرف شواهد، اگر شکاف معنایی واقعی باقی ماند و محاسبهٔ قطعی یا نتیجهٔ معتبر قبلی آن را پوشش نداد، ضرورت API توضیح داده شود. برای Hash، جمع‌زدن، Schema، Join، گزارش‌سازی و بسته‌بندی API مدل لازم نیست.

پیش از Dispatch باید معلوم باشد:

- کدام اقدام و زیرکار به API نیاز دارد و چرا نتیجهٔ قبلی کافی نیست؛
- تعداد پرونده، وظیفه و درخواست تازه، جدا از Cache و Attempt نامعلوم؛
- ورودی، Prompt، Schema، Validator و مدل/مسیر اتصال معتبر؛
- تعرفه و برآورد هزینهٔ همان بسته و رعایت سیاست هزینهٔ جاری پروژه؛
- محل درخواست و پاسخ خام، Checkpoint، خطا، توقف و Resume؛
- نحوهٔ جلوگیری از ارسال دوبارهٔ نتیجهٔ موفق یا تلاش با سرنوشت نامعلوم.

### استفاده از الگوی NB21C و همزمانی ۱۸تایی

کاربر اجرای همزمان ۱۸تایی و جزئیات مسیر API را در بخش‌های مرتبط NB21C معرفی کرده است. هنگام نیاز واقعی، **کد و قرارداد همان اجرای موفق موجود** خوانده و مصرف یا به‌اندازهٔ لازم تطبیق داده شود؛ Runner موازی یا پروفایل اتصال از حافظه ساخته نشود.

عدد ۱۸، سابقهٔ معرفی‌شدهٔ پروژه است؛ مقدار پیش‌فرض همیشگی برای همهٔ وظایف یا تضمین ظرفیت فعلی سرویس نیست. همزمانی، نرخ درخواست، Timeout، Retry، مدل، پارامترها و محدودیت‌ها از کد معتبر همان بسته و شرایط اجرا گرفته شوند. اگر پروفایل‌های تاریخی متفاوت‌اند، مرجع انتخاب با منشأ روشن ثبت شود.

این سند دستور اجرای API نیست و مجوز هزینهٔ مستقل ایجاد نمی‌کند. قواعد جاری هزینه و توقف پروژه حفظ می‌شوند. درخواست و Attempt پیش از ارسال، پاسخ خام پیش از Parse و نتیجهٔ Validation جدا ثبت شوند. Retry پنهان یا خودکار برخلاف قرارداد جاری فعال نشود. Resume فقط کار واقعاً باقی‌مانده را ادامه دهد.

## ۸. خطا، ذخیره‌سازی و اصلاح

خطا در محل تعریف اصلی و با بررسی اثر بر مصرف‌کننده‌ها اصلاح شود. برای تغییر منطق، سل کامل جایگزین و وضعیت Markdown همراه مشخص شود؛ Patch روی History یا تابع تازه برای عبور از Assert داده نشود. سل پولی فقط برای تازه‌کردن کرنل دوباره اجرا نشود.

اگر اقدام خروجی پایدار لازم دارد، نوشتن Atomic، اعتبارسنجی و Reload مستقل مطابق قرارداد موجود انجام شود. اگر اقدام صرفاً خواندنی است، برای اثبات کار فایل و Manifest اضافی ساخته نشود. خروجی سالم و موارد Held کنار هم حفظ شوند؛ چند خطا دلیل بازاجرای کل بسته نیستند.

Golden، Split، Configuration، Rank/Score، پاسخ خام، رأی و شواهد تاریخی بدون مجوز و نسخه‌گذاری تغییر نکنند. Metadata و PASS برای تکمیل ظاهری جدول ساخته نشوند. اجرای پاک، اجازهٔ API تازه نیست؛ Cache ناقص باید توقف روشن بدهد.

## ۹. گزارش پس از خروجی و بستن اقدام

پس از خروجی واقعی کاربر، دستیار مشخص کند:

1. کدام زیرکارها با چه شاهدی تمام شدند؟
2. کدام نتیجه از قبل مصرف شد و چه کار تازه‌ای واقعاً انجام شد؟
3. Validation و Reload لازم چه نتیجه‌ای داشتند؟
4. چه خطا، محدودیت یا زیرکار باقی است و بستهٔ بعد کدام است؟
5. API تازه، Cache، Held و Attempt نامعلوم چه وضعی دارند؟
6. آیا شرط پایان خود اقدام محقق شده یا فقط این بسته تمام شده است؟

تیک فقط مطابق شرط پایان واقعی و دامنهٔ پذیرش ثبت شود. سلامت فنی، اعتبار معنایی، پایان گزارش، PASS کیفیت و پذیرش Release جدا هستند. ثبت مانع می‌تواند کار مستندسازی را ببندد، ولی خود مانع را حل نمی‌کند. تصمیم‌های دامنه‌دار قبلی حفظ شوند و صف قدیمی صرفاً به دلیل تعویض چت دوباره باز نشود.

مخزن و تیک‌ها بدون دستور مستقیم کاربر تغییر نکنند؛ Commit/Push یا ساخت نسخهٔ موازی خودکار انجام نشود. ناظر فقط برای تعارض واقعی دامنه، قرارداد یا پذیرش با شاهد و تصمیم لازم درگیر شود؛ ادامهٔ عادی هر بسته نیاز به اجازه‌خواهی تکراری ندارد.

## ۱۰. ادامه در چت بعدی

برای ادامه، همان ثبت کوتاه اقدام، آخرین خروجی واقعی، شواهد متصل و شکاف باقی‌مانده کافی است؛ منابع تعیین‌کنندهٔ جدید یا متعارض به آن اضافه شوند. دستور مطالعهٔ مشخص کاربر باید به‌طور کامل انجام شود، اما تمام Discoveryهای قبلی بدون علت تکرار نشوند.
