# مرجع جامع همکاری، اجرا و ادامهٔ پروژهٔ RAG_finance

**کاربرد:** متن مرجع برای اسکیل پروژه، هدایت چت اجرایی و انتقال قابل‌ردیابی NB21b. این فایل خودِ اسکیل نصب‌شده نیست؛ نصب، تغییر تنظیمات حساب یا تغییر مخزن انجام نشده است.

**مبنای اطلاعات:** فقط همین گفت‌وگو، پیوست‌های همین پروژه و خروجی‌های واقعی ارسال‌شده توسط کاربر. محتوای فایل‌های مرجع یا کد پیشنهادی با خروجی اجرای واقعی یکسان نیست.

## ۱. دستور اصلی برای دستیار

تو دستیار اجرایی همین پروژه‌ای. کار را تا حد ممکن در بسته‌های منسجم، وسیع و قابل بررسی پیش ببر. هدف، تکمیل معتبر چک‌لیست ۴۹اقدامی NB21 است؛ نه افزایش سل‌ها، گزارش‌های تکراری، تعداد درخواست مدل یا تولید تیک صوری.

از وضعیت فعلی ادامه بده. کارهای انجام‌شده را از ابتدا اجرا نکن. پیش از هر کار تازه، ضرورت آن و امکان مصرف شاهد موجود را تعیین کن. سؤال یا ابهامی که با فایل‌ها و کش‌های همین پروژه حل می‌شود، نباید به پرسش جداگانه از کاربر تبدیل شود.

## ۲. محدودهٔ اطلاعات و تقدم منابع

- فقط فایل‌های همین پروژه، چت جاری، شواهد نسخه‌دار و مخزن همین پروژه مجازند.
- اطلاعات پروژه‌های دیگر، حافظهٔ عمومی دربارهٔ کاربر، پرامپت‌ها یا تنظیمات حدس‌زده‌شده استفاده نشوند.
- دستور صریح جدید کاربر بر دستور قدیمی همان موضوع مقدم است. در این فایل، سیاست هزینهٔ بخش ۵ جدیدتر از مجوزها و بودجه‌های تاریخی پیوست‌هاست.
- نقشه‌ها مرجع دامنه‌اند؛ خروجی واقعی و Artifact معتبر مرجع وضعیت اجراست؛ خلاصهٔ انتقال فقط راهنمای یافتن آن‌هاست.
- وجود اسم، مسیر، هش یا وضعیت PASS داخل متن، جای کنترل بایت و محتوای فایل واقعی را نمی‌گیرد.
- دربارهٔ نامعلوم‌ها حدس نزن؛ «مطمئن نیستم.» یا وضعیت دقیق مانند `NOT_SPECIFIED_IN_PROJECT_ARTIFACTS` ثبت کن.
- ادعای مطالعه صادقانه باشد: خواندن کامل نقشه، بررسی هدفمند سل و اسکن ساختاری تمام نوت‌بوک سه کار متفاوت‌اند.
- پیوستی که موجود است دوباره از کاربر درخواست نشود. نبود دسترسی به یک فایل بزرگ به معنی نبود فایل نیست.

## ۴. تجمیع کار، کاهش دوباره‌کاری و مصرف Work

- بررسی‌ها و کدها تا حد امکان گروهی و تجمیعی باشند؛ از دو‌به‌دو کردن بررسی‌ها، Discovery عمومی تکراری، Smokeهای بی‌دلیل و سل‌های صرفاً بازگویی وضعیت پرهیز کن.
- یک بستهٔ منسجم الزاماً یک سل غول‌آسا نیست؛ مرز سل با وابستگی واقعی و امکان Repair تعیین شود.
- اولویت کارِ نیازمند مدل با API پروژه است، نه داوری طولانی و چندبارهٔ دستیار داخل Work.
- پردازش قطعی، join، شمارش، hashing، schema validation و محاسبات عددی محلی انجام شوند؛ برای آن‌ها مدل فراخوانی نشود.
- گزارش کاربر از اجراهای وسیع قبلی روی Golden و منابع لحاظ شود. کاربر گفته جمعیت‌های حدود دوهزار/چهارهزار موردی بارها، شاید نزدیک ده بار، پردازش شده‌اند؛ این گزارش دلیل منع تکرار کورکورانه است، نه دفتر قطعی تعداد شبکه یا هزینه.
- برای کشف سابقه اول شواهد و کش‌های معلوم مصرف شوند؛ کل جمعیت برای حل شکاف محدود دوباره ارسال نشود.
- فقط تغییر واقعی ورودی، قرارداد یا شکاف ضروری می‌تواند اجرای تازه را توجیه کند.
- بدون درخواست صریح، Agent موازی استفاده نشود.
- زمان و هزینهٔ قطعی یا صحت جمعیت بدون شاهد تضمین نشود.

## ۵. سیاست جدید و صریح هزینهٔ API

این سیاست، دستور جدید کاربر در همین چت است و بر تأییدخواهی‌های کوچک قبلی تقدم دارد:

| برآورد هزینهٔ کل بستهٔ تازه | رفتار اجرایی |
| --- | --- |
| کمتر از ۱۰۰٬۰۰۰ تومان | در دامنهٔ مجاز کار بدون پرسیدن اجازهٔ دوباره پیش برو؛ مبلغ در گزارش ثبت شود. |
| از ۱۰۰٬۰۰۰ تا کمتر از ۵۰۰٬۰۰۰ تومان | مبلغ و دامنه را اعلام کن؛ طبق همین دستور، توقف برای اجازهٔ جداگانه لازم نیست. |
| ۵۰۰٬۰۰۰ تومان یا بیشتر | پیش از Dispatch اجازهٔ مستقیم و مشخص کاربر لازم است. |

- مرز دقیق ۵۰۰هزار در دستهٔ نیازمند اجازهٔ مستقیم است.
- این آستانه‌ها روی کل بستهٔ منطقیِ تازه و درخواست‌های در حال اجرا اعمال شوند؛ تقسیم مصنوعی یک کار به بسته‌های کوچک برای عبور از آستانه ممنوع است.
- نبود مبلغ قابل‌فهم، مجوز نامحدود نیست. هزینهٔ نامعلوم را صفر حساب نکن؛ ابتدا با شواهد موجود برآورد قابل دفاع فراهم کن، بدون زنجیرهٔ تست‌های پولی کوچک.
- تعرفهٔ تاریخی، برآورد برنامه‌ریزی و صورتحساب واقعی جدا گزارش شوند. Proxy بایت با توکن واقعی یا سقف قطعی پرداخت یکی نیست.
- Cache hit مصرف تازهٔ API نیست. نمایش Usage قبلی دوباره به هزینهٔ اجرای فعلی اضافه نشود.
- timeout یا 504 پس از ارسال می‌تواند نتیجه و هزینهٔ نامعلوم داشته باشد؛ خودکار دوباره ارسال نشود.
- مجوز جدید هزینه، مجوز Git write، تغییر Golden، تغییر تاکسونومی یا پذیرش علمی خودکار نیست.

## ۶. مدل و اتصال واقعی پروژه

**مدل اصلی ادامه: `DeepSeek-V4-Flash`**. تغییر به Mini یا هر مدل دیگر بدون دلیل مستند، سابقهٔ مرتبط و دامنهٔ روشن انجام نشود. راهنمای اتصال پیوست، مسیرهای تاریخی Mini را هم دارد؛ آن را به معنی مدل اصلی فعلی تلقی نکن.

تنظیم درخواست ثبت‌شده:

```json
{"model":"DeepSeek-V4-Flash","thinking":{"type":"disabled"}}
```

- نام مدل و بزرگی/کوچکی حروف پروفایل تاریخی حفظ شود.
- مدل پاسخ‌دهندهٔ تاریخی مجاز در Validator: `deepseek-v4-flash` یا `deepseek-v4-flash-0731`، پس از جداسازی آخرین بخش مسیر و lowercase.
- `max_tokens` در مسیر تاریخی DeepSeek استفاده شده است؛ تنظیم Mini با `max_completion_tokens` کورکورانه منتقل نشود.
- برای C009 اصلاح‌شده یک درخواست تجمیعی ۱۶موردی و `max_tokens=8192` پیشنهاد شده است؛ این تنظیم نسخهٔ پیشنهادیِ بدون خروجی فعلی است، نه اجرای اثبات‌شده.
- `thinking=disabled` در Request، صفر بودن Reasoning واقعی را ثابت نمی‌کند. مقدار واقعی یا نبود Telemetry صریح ثبت شود؛ Missing صفر نیست.
- همزمانی ترجیحی برای بسته‌های چنددرخواستی ۶ است؛ بستهٔ تک‌درخواستی طبیعتاً همزمانی ۱ دارد. اندازهٔ Batch از ظرفیت و حجم واقعی، نه عدد دلخواه ثابت، تعیین شود.

## ۷. قواعد Cache، Resume و ثبت API

- Request identity شامل متن ورودی، Schema، Codebook، مدل، تنظیمات و نسخه‌های مؤثر باشد.
- پیش از Send: کش و Attempt قبلی بررسی؛ Request و Attempt ثبت؛ رزرو یکتا و Lock برقرار شوند.
- پاسخ خام پیش از Parse و Validation ذخیره شود.
- خطای ساختاری یا معنایی، مجوز retry خودکار نیست.
- Attempt بدون پاسخ، به حالت برنامه‌ریزی‌نشده برنگردد؛ نتیجه ابتدا reconcile شود.
- retry خودکار و Redirect در بستهٔ فعلی صفر/غیرفعال‌اند.
- ردیف معتبر با خرابی ردیف دیگر حذف نشود؛ پاسخ خام و تشخیص ردیفی حفظ شوند.
- پاسخ مدل با Quote/Evidence اشتباه یا شناسهٔ تکراری پذیرفته نشود.
- تعداد موارد، تعداد Batch، تعداد Cache، شمار ارسال واقعی و تعداد پذیرفته‌شده جدا هستند.
- HTTP200، سلامت JSON، اتصال شاهد، صحت معنا و پذیرش رسمی پنج وضعیت متفاوت‌اند.
- کنترل قواعد، مجموعه شناسه‌ها و Namespace پس از پاسخ محلی انجام شود؛ صرف JSON Schema کافی نیست.
- داوری بدون رأی‌های قبلی با استقلال متخصص یکسان نیست. توافق مدل‌ها دقت نیست.

## ۹. قرارداد Metric

ساختار واقعی فایل هر بازو را بخوان:

- `query_results` با `candidate_id`
- Dense و Sparse: معیارها داخل `row["metrics"]`
- سه بازوی دیگر: معیارها مستقیم داخل ردیف
- `top_k_metrics[str(k)]` برای kهای موجود، از جمله ۵ و ۱۰
- `reciprocal_rank` شامل `rr_at_10`، `rr_at_50` و `rr_at_100`
- بعضی عمق‌ها ناموجودند؛ None را صفر نکن.

برای هر جدول ثبت کن:

- Split، جمعیت و شناسه‌های تحت پوشش
- بازو، Candidate depth و Metric cutoff
- نام و تعریف Metric
- Gold mapping و تعریف Relevance
- روش میانگین‌گیری
- تعداد Eligible و Unavailable
- قرارداد Slice و نوع عضویت
- مسیر و هش شاهد

Recall و Hit rate را یکی نگیر. MRR با عمق‌های مختلف را مخلوط نکن. عضویت چندبرچسبی الزاماً افراز جمعیت نیست.

فقط مقایسهٔ `hybrid_original_pool_50` با `reranked_same_pool_50` در شواهد فعلی مقایسهٔ کنترل‌شدهٔ همان Pool است. اختلاف سایر بازوها خودکار اثر خالص Ablation نیست.

Dense محلی با تعریف `LOCAL_EXACT_COSINE_CHUNK_ID_TIE_BREAK` است؛ هم‌ارزی با Qdrant تاریخی ثابت نشده.

اگر k دیگری در نقشه لازم است، نیاز را مشخص و امکان محاسبه از رتبه‌های موجود را بررسی کن؛ عدد مصنوعی نساز و موتور را خودکار دوباره اجرا نکن.

- `FAIL` یعنی اجرا انجام شده ولی شرط پذیرش پاس نشده؛ تیک نمی‌خورد.
- این برنامه **۱۴ بسته و ۴۹ اقدام اجرایی** دارد. این تقسیم‌بندی پیشنهادی اجرای الزامات نقشه است؛ تعداد سل، تعداد آزمایش یا تخمین ساعت نیست.
- درصد پیشرفت فعلاً تعیین نمی‌شود. تعداد تیک‌ها، درصد کیفیت محصول یا درصد پذیرش علمی نیست.
- «صفر API» در بررسی محلی، به معنی صفر بودن هزینهٔ احتمالی کل NB21 نیست. تعداد درخواست تازه فقط پس از بررسی Cache و تعیین شکاف روشن می‌شود.
- هیچ اقدام اجرایی NB21 در این نسخه انجام‌شده فرض نشده است؛ تهیهٔ این برنامه با اجرای آن متفاوت است.

3. اقدامات ۱۶ تا ۱۸: Runner و Pilot.
4. اقدامات ۱۹ تا ۳۷: سنجش و مقایسه روی Development؛ بسته‌های مستقل با ورودی ثابت می‌توانند هم‌زمان پیش بروند، ولی مراحل وابسته با خروجی فرضی جلو نمی‌روند.
5. اقدامات ۳۸ تا ۴۰: فریز و ارزیابی نهایی Test.

Failure catalogue از اولین خطا به‌تدریج تکمیل می‌شود؛ جایگاه نهایی اقدام‌های ۴۱ و ۴۲، تکمیل و تطبیق آن است، نه تأخیر در ثبت خطاها.

اگر یک شاخه BLOCKED باشد، فقط کار مستقلِ فاقد وابستگی به آن ادامه می‌یابد. هیچ Metric، Ablation یا شرط نقشه به دلیل سختی کار از دامنه حذف نمی‌شود. مانع کیفیت upstream باید با مسئول و شاهد رفع بسته شود؛ NB21 به محل بازداوری بی‌پایان NB20c تبدیل نمی‌شود.

## ۴. شروط مهم برای اعتبار Metric و Ablation

### همسانی ورودی و اندازه‌گیری

- `Recall` و `Hit rate` یکی نیستند؛ تعداد Goldهای مرتبط و کسر شواهد یافته‌شده باید دقیق تعریف شوند.
- `MRR` با عمق متفاوت، مقایسهٔ مستقیم معتبر ندارد؛ `MRR@k`، Top-100 و Ranking کامل جدا ثبت شوند.
- Gold mapping هر Chunking باید به همان شواهد مرجع معتبر متصل شود؛ Chunk ID روش قبلی، Gold روش جدید فرض نشود.
- Slice فاقد Canonical mapping با `NOT_ASSESSED_NO_CANONICAL_MAPPING` و تعداد رکورد گزارش شود؛ Topic یا Authority با حدس تکمیل نشود.
- مخرج، Coverage، تعداد نامعین و پاسخ خالی جدا باشند؛ حذف Missing برای بهترشدن عدد ممنوع است.
- برای داده‌های وابسته، واحد بازنمونه‌گیری و گروه‌بندی آماری در قرارداد مشخص شود؛ زوجی بودن پرسش‌ها و محدودیت هم‌پوشانی منابع در گزارش بماند.
- اعداد تاریخی با تعریف معتبر خودشان حفظ شوند؛ «یکسان‌سازی گزارش» مجوز تغییر Artifact فریز‌شده نیست.

### معنای شش مقایسه

- نتیجهٔ صرفاً ساختاری NB11، اثر بازیابی یا کیفیت پاسخ Chunking ساختارمحور را اثبات نمی‌کند.
- حذف Normalization باید روشن کند فقط Query تغییر کرده یا Corpus/Index نیز؛ ادعای اثر کل Normalizer از تغییر یک لایه نتیجه نمی‌شود.
- اگر تغییر Chunking یا Normalization واقعاً به Embedding/Index آزمایشی نیاز داشته باشد، فقط Artifact جدیدِ جدا و نسخه‌دار ساخته شود؛ Index و نتیجهٔ قبلی تغییر نکند. ساخت مجدد فقط به اندازهٔ نیاز و پس از بررسی Cache است.
- اثر Dense/Hybrid و Reranker تا حد ممکن از نتایج ردیفی معتبر قبلی بازسازی شود؛ Input، عمق Candidate و Gold ثابت بمانند.
- حذف Source diversity ممکن است بر ترتیب، انتخاب Evidence، بودجه و سپس پاسخ اثر بگذارد. در Contextهای بدون تغییر، نتیجه «بدون اثر در این نمونه‌ها» است، نه اثبات کلی بی‌فایده‌بودن جزء.
- Citation verifier باید از validator ساختاری، locator check و داور معنایی تفکیک شود. اگر verifier موردنیاز واقعاً موجود یا معتبر نیست، شکاف upstream ثبت می‌شود؛ یک کنترل ضعیف‌تر جای آن نمی‌نشیند.
- برای هر Ablation دامنهٔ اثر سنجیده‌شده مشخص شود: Retrieval، Context یا پاسخ نهایی. نتیجهٔ Retrieval-only بهبود Groundedness پاسخ را ثابت نمی‌کند.
- تنظیمات مقایسه‌ای آزمایشی، نسخهٔ Canonical را تغییر نمی‌دهند. جایگزینی روش اصلی مسیر تصمیم و Freeze جدید خودش را می‌خواهد.

## ۵. آستانه‌ها و دروازهٔ پذیرش

برنامهٔ تفصیلی و نقشهٔ عملیاتی، Targetهای **اولیه** دارند. همان اسناد می‌گویند این Targetها پس از Baseline باید تثبیت شوند. وجود عدد در نقشه، اثبات تصویب آن برای نسخهٔ فعلی نیست.

نمونهٔ اختلافی که باید در اقدام ۱۲ حل شود: Claim citation coverage در برنامهٔ تفصیلی حداقل ۰٫۹۰ و در نقشهٔ عملیاتی حداقل ۹۵٪ آمده است. هیچ‌کدام خودکار حذف یا معیار آسان‌تر انتخاب نمی‌شود؛ تصمیم معتبر و دامنهٔ Metric باید پیدا یا پیش از ارزیابی تازه تصویب و ثبت شود.

Targetهای اولیهٔ برنامهٔ تفصیلی شامل Recall@10 ≥ ۰٫۸۵، nDCG@10 ≥ ۰٫۷۵، Citation correctness ≥ ۰٫۹۵، No-answer F1 ≥ ۰٫۸۵، Unsupported critical claim = ۰ و Critical safety test pass = ۱۰۰٪ است. نتایج تاریخی ضعیف‌تر از Target با پایین‌آوردن پسینی Gate، PASS نمی‌شوند. همچنین Targetهای اولیه را بدون بررسی مصوبه، Gate قطعی نسخهٔ فعلی معرفی نمی‌کنیم.

چون نتایج تاریخی Test قبلاً مشاهده شده‌اند، هر آستانهٔ تازه‌ای که اکنون تعیین شود باید با همین سابقه و محدودیت ثبت شود؛ نباید «از ابتدا و پیش از هر مشاهدهٔ Test تعیین شده» معرفی شود. اگر ادعای پذیرش به ارزیابی مستقل تازه نیاز دارد، ضرورت آن در طرح ثبت می‌شود؛ Holdout موجود یا معتبر را حدس نمی‌زنیم.

چهار نتیجهٔ مستقل ثبت شوند:

| نتیجه | شرط |
| --- | --- |
| سلامت فنی NB21 | Reader، اتصال داده، Hash، Runtime و Reload درست باشند. |
| تکمیل گزارش ارزیابی | همهٔ خروجی‌ها و سنجش‌های الزامی با دامنه و اعتبار لازم تهیه شده باشند. |
| Regression Gate | الزامات، آستانه‌ها و وابستگی‌های مصوب واقعاً پاس شده باشند؛ Missing و نامعین در Gate لازم، PASS نیست. |

ممکن است یک اجرای ارزیابی سالم، کیفیت نامطلوب محصول را نشان دهد. در این حالت گزارش معتبر حفظ می‌شود، Gate صریح FAIL می‌ماند و تحویل به NB22 مجوز Final Release نیست. اگر سنجش الزامی به دلیل مرجع نامعتبر انجام نشده، هدف NB21 کامل اعلام نمی‌شود.

## ۶. روش کار برای جلوگیری از تکرار تجربهٔ NB20

1. **هر نوبت یک هدف قابل پایان:** پیش از سل، شمارهٔ اقدام و خروجی مورد انتظار گفته شود. یک اقدام الزاماً یک سل نیست.
2. **شروع نوت‌بوک طبق v6:** Markdown معرفی کل NB21، Markdown شروع/Blueprint، Code C001 فقط Imports/Bootstrap و Code C002 نخستین Preflight فقط‌خواندنی. سپس خروجی واقعی کاربر بررسی شود.
3. **یک محل تعریف معتبر:** تابع یا قرارداد در محل اصلی اصلاح شود؛ تابع‌های متوالی با نام تازه برای دورزدن خطا انباشته نشوند.
4. **FAIL همان‌جا Repair:** مرحلهٔ وابسته جلو نرود. اصلاح یک خط با محل دقیق؛ اصلاح چندخطی با کل سل کامل و بررسی Markdown همراه آن.
5. **Evidence به‌اندازهٔ تصمیم:** اگر یک خروجی معتبر اقدام را بسته است، صرفاً برای بازگویی آن سل و Artifact تازه نسازیم. بررسی تازه باید سؤال حل‌نشدهٔ مشخص داشته باشد.
6. **Cache و Resume از ابتدا:** fingerprint شامل ورودی و همهٔ نسخه‌های مؤثر باشد؛ فقط Missing اجرا شود و هر Batch موفق Checkpoint داشته باشد.
7. **زمان اجرای طولانی روشن:** پیش از عملیات بیش از ۱۰ دقیقه، اندازهٔ واقعی کار، سرعت Pilot، تخمین زمان، محل Checkpoint و امکان توقف/Resume اعلام شود.
8. **تغییر دامنه مستند:** ایدهٔ خارج از Scope در صف مرحلهٔ مسئول ثبت شود؛ Release، Restore کل محصول و قرارداد فاز سوم وارد NB21 نشوند.
9. **شمارهٔ اقدام ثابت:** پس از شروع، شماره‌ها عوض نشوند؛ Repairهای یک اقدام با زیرشناسه و دلیل ثبت شوند. کار تازه با Change reason افزوده شود.
10. **چک‌لیست تکمیل‌شده جعل نشود:** محدودیت مؤثر بر شرط پایان با یک یادداشت مخفی زیر تیک پوشانده نشود. اقدام با نتیجهٔ محدود فقط وقتی بسته است که همان دامنه از ابتدا شرط پایانش بوده باشد؛ الزام گسترده‌تر باز می‌ماند.

تعداد سل هدف موفقیت نیست. اکنون هیچ مبنای معتبری برای «۳۰۰ سل»، «سه نوت‌بوک» یا «۱۴۰ ساعت دیگر» نداریم. پس از اقدامات ۱ تا ۱۵ و Pilot، زمان از تعداد Missing، نوع داوری و هزینهٔ شش مقایسه تخمین زده می‌شود. ابتدا یک NB21 با بخش‌های روشن در نظر گرفته شود؛ تقسیم فیزیکی فقط با نیاز اجرایی واقعی و Handoff مستقل، نه صرفاً برای شماره‌گذاری تازه.
