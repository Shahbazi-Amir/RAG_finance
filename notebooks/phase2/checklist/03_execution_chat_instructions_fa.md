## ۴. اولین پاسخ تو چه باشد؟

اگر بعد از C069 سل دیگری اجرا شده، اول همان خروجی را مصرف کن. اگر پاسخ استرا هنوز نیامده:

- بازبینی استرا را انجام‌شده فرض نکن؛ Metric، داوری یا کد مدل تازه ارائه نده.
- برای رفع نیاز دسترسی، فقط فایل دقیق موجود را بخواه یا با کد آفلاین و مجاز، از دفتر ورودی موجود بخوان؛ گزارش موازی تازه نساز.

پس از رسیدن پاسخ استرا:
۱. حداکثر چند بند دربارهٔ توافق/اختلاف ضروری بده.

۳. فقط یک بستهٔ کامل بعدی را با شرط توقف و پایان ارائه کن.

اگر فایل تعیین‌کننده در دسترس نیست، اسم و مسیر دقیق و تصمیم وابسته را اعلام کن؛ عبارت مبهم «فایل‌ها را دوباره بفرست» نگو. دسترسی Remote را معادل موجودی مک فرض نکن.

## ۵. اولین بستهٔ کدنویسیِ مجاز پس از بازبینی روش

شمارهٔ سل را از نسخهٔ واقعی انتخاب کن؛ «C070» فقط اگر خالی و درست باشد. این سند کد آن را اجرا یا رزرو نمی‌کند.

بسته باید تا حد ممکن در یک سل کامل، فقط کارهای ضروری زیر را انجام دهد:
- بارگذاری Receipt معتبر C069 و ورودی موردنیازِ همان مرحله با مسیر و Hash صریح.
- مصرف نتایج سالم قبلی؛ شمارش و تطبیق اضافه فقط وقتی برای تصمیم استفاده می‌شود.
- اگر annotated/پرچم‌ها/تکرارها مصرف می‌شوند، کنترل هدفمند اتصالشان به source و proposals.
- ثبت قرارداد مصوب و منشأ تصمیم یا وضعیت pending؛ پیشنهاد را approved نکن.
- ساخت/به‌روزرسانی دفتر موجود برای scope، relevance، support، unjudged و منشأ بازبینی؛ فیلدهای ثبت‌شده از روی Schema واقعی خوانده شوند.
- گزارش کار واقعاً باقی‌مانده با تعداد سؤال، جفت و درخواست جدا؛ بدون پیشنهاد API خودکار.
- ذخیرهٔ نسخه‌دار، حفظ فایل اصلی، Validation/Reload و گزارش Fact/Interpretation/Pending.
- یک گام بعدی واحد. این بسته خودش داوری معنایی انجام‌شده یا Reference qualification ایجاد نمی‌کند مگر ورودی تصمیم معتبر آن ارائه شده باشد.

کد برای مرحلهٔ بعدی باید با Schema و تصمیم واقعی تطبیق داشته باشد؛ جای خالی قرارداد را با default موفق یا Enum حدسی پر نکن.

## ۶. قوانین غیرقابل حذف در بازبینی و سنجش

- ارتباط بازیابی، کفایت پاسخ و صحت اتصال Locator جدا هستند.
- PARTIAL به‌طور خودکار NOT_RELEVANT نیست؛ هم‌Locatorبودن به‌تنهایی RELEVANT نیست.
- متن سؤال و انتظار پاسخ، داده‌اند؛ انتظار پاسخ تنها پاسخ مجاز نیست.
- شواهد خارج از برگهٔ ۱۹۷جفتی unjudged هستند؛ منفی فرض نشوند.
- حفظ جمعیت یعنی حسابداری شفاف؛ ابهام را برای ثابت‌شدن مخرج به صفر یا رأی قطعی تبدیل نکن.
- نمونهٔ ۱۲تایی هدفمند است؛ به ۲۴، ۵۳۳ یا ۲۶۶۴ تعمیم نده.
- تعداد قضاوت مدل و تعداد برچسب پذیرفته‌شده یکی نیستند.
- اگر بازبین پیشنهادها یا annotated را دیده، independent blind review ادعا نکن.
- ارزیابی استرا از روش، تأیید رسمی ۱۹۷ برچسب نیست؛ استرا نیز مدل است.
- duplicate passage با Chunk ID متفاوت طبق واحد فعلی حفظ شود؛ ادغام تغییر قرارداد می‌خواهد.
- historical Gold، داده، split، رتبه‌ها و پاسخ‌های خام بدون نسخه و تصمیم صریح تغییر نکنند.
- آستانه‌ها برای PASS پایین نیایند؛ عدد جدید با تعریف جدید، بهبود موتور نام نگیرد.
- چهارخانهٔ مقایسه فقط روی دامنهٔ مشترک و مرجع دارای مصرف مجاز ساخته شود؛ اگر مرجع پیشنهادی است، خروجی صرفاً تشخیصی باشد.

## ۸. قالب پاسخ اجرایی

خروجی معمول همین چت:
۱. نتیجه و دامنهٔ کار، کوتاه؛
۲. **یک باکس Markdown برای سل Markdown**؛
۳. **یک باکس Python برای سل کامل کد**؛
۴. خروجی مورد انتظار و شرط توقف/پایان.

فایل دانلودیِ Python یا Markdown جای باکس سل اجرایی در چت نیست، مگر خود کاربر بخواهد. برای نقشه و سند انتقال، فایل Markdown تحویل داده شده؛ این قاعدهٔ فایل با قاعدهٔ سل اجرایی متفاوت است.

زمان بیش از پنج دقیقه را پیش از اجرا با مبنا اعلام کن. اجرای سنگین با checkpoint و Resume واقعی؛ برآورد ضمانت نیست. این پیام مجوز هیچ محاسبهٔ سنگین تازه‌ای نمی‌دهد.

## ۹. شرط پایان بستهٔ فعلی

بسته زمانی بسته است که معلوم شود:
- کدام برچسب‌ها صرفاً پیشنهادند و کدام با چه منشأیی قابل مصرف‌اند؛
- مرجع چه دامنه‌ای را پوشش می‌دهد و چه چیزی unjudged/نامعین مانده؛
- از رتبه‌های موجود چه مقایسهٔ معتبر یا تشخیصی می‌توان گرفت؛
- کدام شکاف واقعی است و یک گام بعدی چیست.

تمام ابهام‌ها لازم نیست حل شوند تا گزارش تمام شود. اگر پذیرش رسمی ممکن نیست، علت دقیق BLOCKED ثبت و تحلیل محدود به پایان برسد؛ دنبال قبولی اجباری نرو.
